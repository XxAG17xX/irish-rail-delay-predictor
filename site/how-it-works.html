How it works.

Five minutes for the whole thing. Anything marked with an arrow can be opened for the detail, and skipped without losing the argument.

1. The question

Station boards tell you a train is expected at 17:27. They do not tell you how sure they are. A train that has been steadily two minutes late for five stops and a train that has just picked up an unexplained delay both get the same kind of estimate: one time, stated with the same confidence.

RailCast answers with a range instead. Not "17:27" but "most likely 17:26, probably between 17:22 and 17:34". The range is the useful part. If you have a four minute connection at the other end, a two minute range says you are fine and a twelve minute range says you might not be. A single number cannot tell you that.

The formal name is a prediction interval: a low bound and a high bound, chosen so the true answer falls between them a stated share of the time. This one aims for 80%, so the claim is "four times in five". That is a claim you can check, which is the whole point of the accuracy page.

What it refuses to answer. It does not forecast future dated services. Every input describes a journey in progress, so a train that has not departed leaves nothing to reason from. Ask about tomorrow's 08:15 and the honest answer is that this system has nothing to say, so it declines instead of guessing. A visitor expecting next week's forecast will think it is broken. It answers about trains that are already running.

2. Where the numbers come from

Irish Rail publish a realtime feed. No sign up, no key, and no promises: they state it is provided as is, with no support. Four parts of it are in use.

  • One train's full journey on one date. Every stop, the scheduled time, and the actual arrival if one was recorded. This is the whole project. It is the record of what really happened, and it is what the model learns from.
  • A station's board. What is due in the next ninety minutes, including Irish Rail's own expected arrival. That field is the baseline being competed against, and it has to be captured live because it cannot be recovered later.
  • Which trains are running right now, which is how the system knows what it can be asked about.
  • The station list, fetched once and cached.
How do you know the feed serves real history rather than replaying a timetable?

By asking for the same train on the same date in 2020, 2024, 2025 and 2026. The times all differ, and the 2020 version has three fewer stops and a different scheduled arrival at Cork, which is the 2020 timetable on 2020 infrastructure. It is genuine history, back to at least 2007.

That single check is what makes a missed collection run recoverable. It does not apply to the operator's expected arrival, which exists only live and can never be backfilled, which is why a poller has been running every five minutes since August.

The training archive is 28,706 gzipped responses covering 1,087 train codes across 34 dates, about half a million stop level records, collected once at two requests per second, overnight, backing off whenever the server complained.

3. The problem that shaped everything

To learn how late trains are, you need to know how late trains were. That true arrival time is the label, the right answer a model is trained against. The feed has a field for it. But on parts of the network the operator does not actually observe arrivals, and the field comes back holding the timetable, presented as though it were an observation.

It looks completely normal. Nothing marks it. Train on it and the model learns that those lines are perfectly punctual.

Call it an echo: the schedule reflected back, dressed as a measurement. You can look for it, because a real arrival almost never lands on exactly the scheduled second. Across the whole archive, 2.92% of arrivals are identical to the scheduled time.

Irish Rail document this and publish a list of ten lines where the query returns the scheduled time only. So the obvious fix is to distrust those lines. Tested, it looked like clean confirmation: the flagged lines matched exactly 21% of the time against under 3% everywhere else. An eightfold difference.

It was the wrong conclusion. Every arrival record also carries a flag saying whether the time was captured automatically by the signalling equipment. Split by that instead, and the comparison reverses: among machine captured records, the flagged lines echo less than the rest of the network.

What made the flagged lines look bad is that far more of their records were not machine captured: 47% against 1.5% elsewhere. The non-automatic ones are where echoes live. The lines were not worse. Their data was captured differently.

A comparison that reverses when you split it has a name: Simpson's paradox. Three quarters of the suspect records sit on lines the documentation never mentions, so a line filter would have thrown away good data and kept bad. The rule became: use the per record capture flag, never the published line list.

Why nothing is deleted, even when it looks obviously wrong

An exact match is suspicious, not proof. About 2.4% of the most trustworthy records genuinely do land on the scheduled second. Part of the reason is that every time in the feed is rounded to six seconds, so there are only ten possible second values in a minute and coincidences are commoner than they look.

So nothing is deleted at ingestion. The flag is carried through, what to exclude is decided when evaluating, and the numbers are reported both ways. A result that agrees with the documentation is exactly the one nobody checks carefully enough, and this one was wrong.

4. The model

One model for the whole network, not one per train. It is a set of gradient boosted trees, a method that builds many small decision trees where each one corrects what the ones before it got wrong.

What makes a range possible is the loss function. An ordinary model is trained to be wrong by as little as possible in both directions, which gives you a middle. A quantile model is trained with lopsided penalties: to learn the ninetieth percentile, being too low is punished nine times as heavily as being too high, so it settles where 90% of outcomes fall below. Train three of them, at the tenth, fiftieth and ninetieth, and you have a low bound, a most likely value, and a high bound.

The rule that governs every input

Features describe the situation, never the identity. The train code is not an input. A service launched next March would arrive as an unknown category, and a model that had learned "A218 runs two minutes down" would have nothing to say about it, or about the same service after a renumbering.

What it uses instead: delay accumulated upstream today, stops and minutes remaining, time of day, day of week, and a route proxy. All twelve inputs exist for a train that started running yesterday. The strongest by far is the delay at the previous stop, because lateness carries forward along a journey.

The three models are trained separately, so what stops them disagreeing?

Nothing forces them to agree, so occasionally the tenth percentile comes out above the ninetieth. That is called quantile crossing. The fix is to sort the three values at prediction time, which is provably no worse than leaving them crossed.

There is also a rule about what is never allowed as an input: the operator's own expected arrival. It is the baseline being compared against, so feeding it in would make the comparison meaningless.

5. How it is measured

The headline claim is a head to head against Irish Rail's own expected arrival time. That is the right baseline because it is what a passenger would otherwise be reading. Beating a naive guess would prove nothing.

Three rules make the comparison fair, and each exists because ignoring it produces a flattering wrong number.

  • Matched events only. A result counts only where both the model and the operator produced a prediction for the same train, at the same station, at the same moment. Comparing all of one against all of the other compares populations, not methods.
  • One result per event, not per poll. A single arrival is polled about eighteen times as the train approaches. Treating those as eighteen independent results inflates the sample size roughly eighteenfold and makes noise look significant.
  • Matched precision. The operator publishes to the minute and the model to the second. Scoring second precision against a minute rounded baseline hands the model an advantage it did not earn, so its answer is rounded to match before either is scored.

A week of data, 20 to 26 July, has never been opened and stays sealed until the end. Every offline number quoted anywhere in this project is validation, not test. A test set you have looked at is no longer a test set.

Nothing is reconstructed after the fact. Every prediction is written to storage the moment it is made, with a timestamp and the model version. The nightly scorer can read that log and has no permission to write to it, and that is enforced by the AWS credentials the job runs with rather than by anyone remembering. It is the difference between a claim and a checkable claim.

6. What is actually running

Everything is a scheduled function writing to object storage. There is no database and no server that stays up: the read pattern is "give me one whole day", the write pattern is append only, and neither needs one. The whole thing costs about ten cents a month, almost all of it storage requests.

Why is there a generator asking the service questions?

Because almost nobody visits this site, and an accuracy page built on a handful of the author's own test queries would be worthless. So a scheduled job asks the live service a spread of questions every five minutes, one per lead band, sampled across whatever is in service rather than favouring any route.

Those are real predictions, made before the outcome existed. They are simply not anyone's. The accuracy page says so rather than implying traffic that does not exist. Board views from this site are logged separately, so the two can always be told apart.

7. What it cannot do

The ranges do not cover disruptions

On real delays over an hour, coverage is zero, and it was zero for the previous model too. When three Sligo line trains each lost seventy five to ninety minutes in a single stretch, the service had been asked sixteen times across those journeys, and at every one of those moments the train was two to seven minutes late.

This is a limit of the approach rather than a bug to be tuned out. A wider range would mean being wrong about ordinary days to hedge against rare ones. The ranges are calibrated for ordinary lateness.

  • No upstream report, no prediction. Every input is derived from where the train has already been, so the service declines rather than guessing, and the decline rate is published beside the accuracy rather than left out of it.
  • Coverage has two honest denominators. Given a train actually in service, it answers about nine times in ten. Standing in front of a station board the figure is far lower, because roughly four in ten board entries are trains that have not departed.
  • Two corridors are below the promise right now. The Cork and Kildare corridors are covering nearer two times in three than four in five. They share track, and the rest of the network is unaffected, which reads as the railway changing rather than the model breaking. It is published per line rather than blended into one number.
  • It is not a route planner. No map, no accounts, no notifications. Each of those costs a week and answers nothing this project set out to answer.

8. The thing that kept happening

Eleven separate failures in this project shared one shape. None raised an error. None appeared in a log as a problem. Every one produced output that looked exactly like a correct, unremarkable result, and every one was caught the same way: by taking a number and asking what it should have been.

What it looked likeWhat it was
Flagged lines reporting arrival times Scheduled times echoed back as though observed
420 successful downloads, HTTP 200 An internet provider's login page, 1,369 identical bytes each time
A deploy reporting success on an alarm A subscription nobody confirmed, deleted 48 hours later. Alerting was dead and looked fine
A model with a 22 minute average error Two ways of computing "late" that disagreed by a day. No model change fixed it
Arrival times marked machine verified Real times, captured by real equipment, filed against the wrong train
A model covering a quarter of severe delays Every covered case was a wrong label matched by a range learned from the same wrong labels
A rebuild that "completed, exit code 0" It had crashed on its first line. The exit code belonged to the command after the pipe
A nightly job printing a healthy report It ran out of memory four minutes later. A frozen page and a working one look identical

Four of these were introduced by me, after the system was working, while writing up the others. The lesson is not "be more careful". It is that a system which works and a system you can tell is working are different things, and most of the effort here went into the second.

The uncomfortable version of the question

How many failures of this shape are still in the project, undetected, right now?

Almost certainly some. The honest answer is that the count of eleven is a count of the ones that were caught, and the only reason any of them were caught is that each published number has a denominator attached to it and a check that asks what it should have been. That is the design, and it is the argument for publishing where the model loses rather than only where it wins.
